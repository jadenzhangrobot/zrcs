1. 为什么需要段间加速度衔接

路径被拆成一串几何段（直线 + 拐角圆弧）后，若只规划接点速度 v_enter / v_exit，而每段入口/出口加速度默认全 0， Ruckig 在段切换时会强制把加速度拉回 0，再重新爬升——速度曲线会出现 “锯齿状” 加速度脉冲，S 形变差，时间也更长。

只连续速度（a≡0）

每段边界强制 a=0。段间速度连续，但加速度跳变；跨段加速过程被反复打断。

速度 + 加速度联合连续

上一段 a_exit = 下一段 a_enter。 Ruckig 可在整条路径上保持平滑加减速，更接近全局 S 曲线。

本工程的做法是： 先固定接点速度，再在离散加速度候选上做最短时间动态规划， 选出一套全路径一致的接点加速度。

2. 整条规划流水线

编排入口在 MotionPlanner::plan()：

几何定形 → 速度前瞻写边界 → RT 按段 Ruckig 在线插补

第 ④ 步 LookAheadPlanner::planSegments() 内部又分 6 小步。 段间加速度衔接是第 6 小步，前提是接点速度已经冻结。

3. 状态量与数据契约

几何段 + 速度结果都落在 TrajectorySegment （TrajectoryTypes.h）：

字段含义谁写入
length段弧长 L (m)几何阶段
v_max_local段内速度上限前瞻第 1 步
v_enter / v_exit入口 / 出口速度前瞻第 5 步
a_enter / a_exit入口 / 出口切向加速度前瞻第 6 步 ★
duration该段 Ruckig 最短时间估计前瞻第 6 步
衔接约束（工程保证）
对相邻段 i−1 与 i：
segments[i-1].v_exit == segments[i].v_enter  // 同一接点速度
segments[i-1].a_exit == segments[i].a_enter  // 同一接点加速度
路径起点强制 a_enter = 0，终点强制 a_exit = 0 （静止边界）。

注意：这里的加速度是路径弧长参数 s 上的切向加速度 a = d²s/dt²，不是笛卡尔各轴加速度，也不是法向加速度。

4. 先定速度：1–5 步（为加速度铺路）

  1. 段内速度上限 v_max_local = min(全局 maxVel, 编程进给 F, √(a_max / κ))。 曲率大的圆弧自动降速。
  2. 几何接点限速 拐角容差模型 v² ≈ a·cornerTol / (1−cosθ)， 再叠加曲率跳变的 jerk 约束。
  3. 反向扫描 从终点往前：若入口速度过高，在本段长度内刹不到后续接点，则压低入口。
  4. 正向扫描 从起点往后：若出口速度过高，本段加速不到，则压低出口。
  5. 写回 v_enter / v_exit 冻结。此后速度不再改，只选加速度。

步骤 3/4 里“能不能到”用的是简化 S 曲线距离估计 dMinTransition(v0,v1)：

T = 2·√(Δv / j)   若峰值加速度 √(j·Δv) ≤ a_max
T = 2·(a/j) + (Δv/a − a/j)   否则（梯形加速度剖面）
d = 0.5 · (v0 + v1) · T
这只是速度可达性的快速估计，还不考虑边界加速度 a0, a1。真正带 a 边界的可行性，留给第 6 步用完整 Ruckig 判定。

5. 核心：接点加速度联合规划

实现函数： LookAheadPlanner::planJunctionAccelerations() （LookAheadPlanner.cpp）。

接点 J 上速度已固定，加速度从候选集合中选；相邻接点对用 Ruckig 评估段时间

算法结构一句话：

状态 = (接点 i, 候选加速度 a_k)
边代价 = Ruckig 从 (v_i, a_k) 转移到 (v_{i+1}, a_m) 走完 L_i 的最短时间
目标 = 从起点 a=0 到终点 a=0 的最短总时间路径

6. 加速度候选如何生成

对每个接点 i，构造候选集合 A_i：

接点类型候选集合
起点 / 终点 / 速度≈0 的接点 只保留 {0}
中间接点
  1. 均匀采样： a = maxAccel · s / 8， s = −8…+8（共 17 个）
  2. 物理启发项（再 clamp 到 ±a_max）：
    • 左等价：(v_i² − v_{i−1}²) / (2 L_{i−1})
    • 右等价：(v_{i+1}² − v_i²) / (2 L_i)
    • 中心估计：跨两段的平均加速度
  3. 排序 + 去重（|Δa| ≤ 1e-10 视为相同）
为什么要加“等价加速度”？
匀加速近似 v² = v0² + 2 a L 给出的 a，往往接近真实最优边界。 把它塞进候选，可避免纯均匀网格错过好点；再靠 Ruckig 做精确可行性过滤。

7. 动态规划目标与递推

7.1 代价定义

costToEnd[i][k] = 从接点 i 选加速度候选 k 出发，到路径终点的最短剩余时间

边界：终点接点只有 a=0，costToEnd[N][0] = 0；其它为 +∞。

7.2 反向递推

从最后一段往前扫：

对每个当前候选 k、下一接点候选 m：
  d = transitionDuration(L_i, v_max_local_i, v_i, a_k, v_{i+1}, a_m)
  若 d 有限：candidate = d + costToEnd[i+1][m]
  取最小者写入 costToEnd[i][k]，并记录 nextChoice[i][k] = m 
// 反向 DP 核心循环（示意）
for (i = N-1 … 0) {
  for (k in A_i)
    for (m in A_{i+1})
      d = transitionDuration(L_i, v_max_i, v_i, a_k, v_{i+1}, a_m);
      if (finite(d) && d + costToEnd[i+1][m] < costToEnd[i][k]) {
        costToEnd[i][k] = d + costToEnd[i+1][m];
        nextChoice[i][k] = m;
        chosenDuration[i][k] = d;
      }
}

7.3 前向回放

起点只有 a=0（候选下标 0）。若 costToEnd[0][0] 仍为 ∞， 整条路径无解，前瞻失败。 否则沿 nextChoice 回放：

segments[i].a_enter = A_i[current]
segments[i].a_exit = A_{i+1}[nextChoice[i][current]]
segments[i].duration = chosenDuration[i][current]
current ← nextChoice[i][current]

这样自然满足 segments[i].a_exit == segments[i+1].a_enter—— 段间加速度衔接是 DP 状态共享的直接结果，不是事后修补。

8. Ruckig 可行性判据

边代价由 transitionDuration() 计算：对单段构造一次 离线 Ruckig 求解。

Ruckig 输入取值
current_position0
current_velocity / accelerationv0, a0（本段入口）
target_positionL（段长）
target_velocity / accelerationv1, a1（本段出口）
max_velocity该段 v_max_local
min_velocity{0}（离线评估时禁止倒退）
max_acceleration / max_jerk全局 maxAccel / maxJerk
result = otg.calculate(input, trajectory)
若 result < Working 或 duration 非法 → 返回 +∞（该边不可行）
否则返回 trajectory.get_duration()
关键点：NRT 前瞻用 Ruckig 离线 评估边是否可行； RT 的 MovePath 再用 Ruckig 在线 按同一边界插补。 两边约束一致，才能避免“规划通过、执行 -110”。

9. 下发到 RT 的衔接方式

NRT 侧 PathMoveSupport::fillMovePathArgs() 把每段打成一条 MovePath 命令： 

args[Vel]       = segment.v_max_local   // 段内上限
args[TargetVel] = segment.v_exit        // 出口速度
args[TargetAcc] = segment.a_exit        // 出口加速度 ★ 衔接关键
args[Sync]      = (i == 0) ? 1 : 0      // 仅首段重置弧长状态

同时 setPathMoveConfig(maxVel, maxAccel, maxJerk) 写入共享内存，供 RT 读加速度 / jerk 上限。

RT 侧 MovePath::initTrajectory()：

  • 首段 Sync=1：重置 s=0, v=0, a=0
  • 后续段：不重置，靠 output.pass_to_input(input) 继承上一段结束时的 (s, v, a)
  • 本段目标设为： target_position = 累计弧长， target_velocity = v_exit， target_acceleration = a_exit
跨段不重置 Ruckig 状态；连续性靠 NRT 写出的 a_exit 与 RT 继承的 a 对齐

10. 数值直觉示例

假设三段直线，接点速度已定为：

v = [0, 0.03, 0.05, 0] m/s
L = [0.02, 0.03, 0.02] m
a_max = 0.5 m/s²,   j_max = 3.0 m/s³

DP 可能选出类似：

段v_entera_enterv_exita_exit含义
0000.03+0.25 从静止加速，出口仍带正加速度
10.03+0.250.050 继承正加速度继续加速，出口拉平
20.05000 匀速后减速到停

若强制所有 a=0，段 0 必须“加速到 0.03 且出口 a=0”，段 1 再从 a=0 重新加速—— 中间多一次不必要的加减速折返。联合选 a 后，加速过程可以跨段延续。

11. 常见坑与 result=-110

ErrorExecutionTimeCalculation (-110)
Ruckig 在给定边界 (v0,a0)→(v1,a1)、距离 L、以及 v/a/j 限制下找不到可行轨迹。
现象原因本工程对应
jerk 调小后 RT 报 -110 可行域变窄；在线状态与目标边界对不齐时更易无解 前瞻用完整 Ruckig 过滤边；但在线还有数值误差
min_velocity=0 加剧失败 禁止弧长速度短暂为负，砍掉部分数学解 NRT 评估带 min_v=0；RT MovePath 若也强加，低 jerk 时更脆
短段 + 非零 a_exit 距离不够完成 a0→a_peak→a1 的 jerk 爬升 DP 会判该边 ∞；若在线状态漂了仍可能炸
上一段结束 a 与下一段目标不一致 衔接断了 正常 DP 回放保证一致；Sync 误用会重置状态
设计取舍
离线前瞻在 transitionDuration 里设置了 min_velocity={0}，保证规划出的边界“按理”可在非负速度下走完。 在线侧若额外加同样硬约束，会把数值误差的容错吃光。 更稳妥的是：规划保证 v≥0，在线只限上限，靠 pass_to_input 继承状态。
