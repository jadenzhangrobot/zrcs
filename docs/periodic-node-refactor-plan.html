1. 背景与问题

1.1 现状

当前 zrcs_rt 定义了三种节点类型（BaseNodeInterface.h）：

  • CmdNode — 事件/命令驱动，按 CmdId 路由，有 INIT→RUNNING→EXIT 状态机（Enable/Disable/MoveL/MoveJ…）。
  • OutputNode — 周期驱动，调度在周期后半段（PlcLogicNode、MujocoIdentPub、ContinuousJog）。
  • InputNode — 周期驱动，调度在周期前半段（DataPub）。

1.2 核心矛盾

  • OutputNode 与 InputNode 结构几乎完全相同：同样只有 std::atomic<NodeStatus> nodeStatus_，同样的 init()/run()/execute() 状态机，重复代码见 BaseNodeInterface.h L181-239。
  • "长期节点"被硬拆成两个名字，但二者本质都是"每周期常驻执行"。
  • 组内执行顺序不可控：NodeFactory 按静态注册顺序（链接顺序）填充 vector，没有优先级字段，顺序"看缘分"。
  • 语义混乱实证：ContinuousJog 名字像命令、会做 Ruckig 速度规划，却因用标志位触发而继承了 OutputNode——"Input/Output/Command"三个名字无法刻画"常驻 + 会规划"。
  • 执行顺序现状：跨组（先输入后输出）是 NodeManager.cpp 里写死的两段循环（L152 / L233）；组内无显式排序。

1.3 诊断结论

真正的本质差别只有一个正交维度：

  • 触发方式：命令事件（CmdNode） vs 每周期常驻（长期节点）。

因此把长期节点统一为 PeriodicNode，并用 Phase（硬相位）+ execOrder_（组内软排序） 表达顺序，是贴合语义且低成本的最优解。CmdNode 是真正的第二类，保持不动。

2. 目标与不做的事

2.1 目标

  1. 消掉 InputNode/OutputNode 的类型重复，统一为 PeriodicNode。
  2. 让长期节点的执行顺序显式、可读、可维护（Phase 硬约束 + execOrder_ 软排序）。
  3. 保持 1ms RT 硬实时约束：无分配、无异常、无阻塞。
  4. 保持现有行为语义不变（先采后发的相位次序不回归）。

2.2 明确不做（范围外）

  • 保持 CmdNode 完全不动——事件驱动与周期驱动是正交语义，合并反而错误。
  • 不做 不引入数据流 DAG / 拓扑排序（对 1ms 硬实时负担过重）。
  • 不做 不把 PLC 拆成独立实时线程（见 1.2 既定结论）。
  • 不做 不改调度相位总顺序：输入 → 命令 → 输出。

3. 目标架构设计

3.1 类型层次

// BaseNodeInterface.h
class Basenode { /* …现有公共基类不变… */ };

enum class NodePhase { INPUT, OUTPUT };  // 硬相位

class PeriodicNode : public Basenode {
public:
    std::atomic<NodeStatus> nodeStatus_{NodeStatus::RTINIT};
    NodePhase   phase_{NodePhase::INPUT};  // 由子类或宏指定
    uint32_t    execOrder_{0};                     // 组内相对顺序，越小越先

    virtual void init() = 0;
    virtual void run()  = 0;
    virtual void execute();   // 状态机：RTINIT→EXECUTING→FAILED
};

// 命令节点独立保留（事件驱动）
class CmdNode : public Basenode { /* …不并入 PeriodicNode… */ };

3.2 顺序模型：Phase（硬）+ execOrder_（软）

  • Phase 是硬约束：所有 INPUT 必然先于所有 OUTPUT，中间夹速度规划命令。保证"先采数据 → 再规划 → 再发数据"的确定性。
  • execOrder_ 是组内软排序：同一相位内按 execOrder_ 升序执行，同值用注册顺序兜底（stable_sort）。
  • 排序只发生一次：在 NodeManager::run() 启动前对两个（或一个）vector 排序，RT 循环内不再排序（零运行时开销）。
排序时机放在 RT 任务启动之前（与 registered()、prepare() 同阶段），RT 循环内严格线性遍历，满足实时规范。

4.1 基类接口（BaseNodeInterface.h）

5. 注册机制与宏改造（NodeFactory）

5.1 存储结构：两个容器 vs 一个容器

为保证调度仍走"输入段 / 输出段"两段（保留相位硬约束），保留两个 vector，只是元素类型统一为 PeriodicNode。

class NodeFactory {
public:
    std::vector<std::shared_ptr<PeriodicNode>> inputPeriodics;   // Phase::INPUT
    std::vector<std::shared_ptr<PeriodicNode>> outputPeriodics;  // Phase::OUTPUT

    // 仅用于命令节点（保持现状）
    Creator getNodePtr(CmdId id) const;
    // 启动前调用一次，按 execOrder_ stable_sort 两组 vector
    void sortPeriodics();
};

5.2 宏定义（NodeFactory.h）

// 新宏：注册一个长期节点，显式指定相位与组内顺序
#define REGISTER_PERIODIC(className, phase, order)                              \
    static ::zrcsSystem::RegisterPeriodic<class className> reg_##className(       \
        ::zrcsSystem::NodePhase::phase, static_cast<::std::uint32_t>(order))

// 旧宏保留为兼容薄封装（内部转发到 REGISTER_PERIODIC，便于渐进迁移）
#define REGISTERINPUT(className)  REGISTER_PERIODIC(className, INPUT, 10)
#define REGISTEROUTPUT(className) REGISTER_PERIODIC(className, OUTPUT, 10)

5.3 注册 helper（NodeFactory.cpp）

template<typename T>
class RegisterPeriodic {
public:
    RegisterPeriodic(NodePhase phase, uint32_t order) {
        auto node = std::make_shared<T>();
        node->phase_     = phase;
        node->execOrder_ = order;
        if (phase == NodePhase::INPUT)  NodeFactory::pendingInputs().push_back(std::move(node));
        else                              NodeFactory::pendingOutputs().push_back(std::move(node));
    }
};
注意：std::make_shared 目前发生在静态初始化期（与现状一致）。RT 规约要求"RT 循环内无分配"——静态期分配合规，但需保持 NodeFactory 构造期完成 drain，切勿把分配挪进 run()。

6. 调度器改造（NodeManager）— 详细

6.1 现状调度器结构（改造前，必须先精确掌握）

唯一的 RT 实时线程跑 NodeManager::run() 里 real_task 注册的回调（NodeManager.cpp L83-316），每个周期严格按以下顺序执行：

// ── RT 周期（1ms）顶层顺序 ─────────────────────────────────────
L85  controller_->receiveData();                  // ① 读总线/反馈
L86  读 shm()->taskSched（观测状态）→ taskScheduling_
L146 轴故障检测 → 可能切 ERROR_STATE
L152 ── 输入段 INPUT（Phase 前置，switch 之外，所有状态都执行）──
L168 switch (taskScheduling_)
    L170 case RUN:
        L171 命令节点调度（取命令 → execute → 结果/失败处理）
        L233 ── 输出段 OUTPUT（case RUN 之内，仅 RUN 执行）──
L296 taskSched 回写（compare_exchange）
L302 controller_->sendData();                    // ⑥ 下发位置指令（所有状态）
L306 sendData 后故障补检 + 心跳
必须保留的不对称语义（本次重构不能改变）：
  • 输入段（INPUT）在 switch 之外 → 对 STOP/ERROR/RESET/IDLE/RUN 全部执行。
  • 输出段（OUTPUT）在 case RUN 内部 → 仅 RUN 状态执行（这点符合 PLC/联锁"运行期才输出"的现状设计）。
  • 命令段同样仅 RUN；sendData() 对所有状态执行。

6.2 目标时序（改造后）：排序只做一次，相位语义完全不变

改造后周期结构仍在同一位置调用同一遍历逻辑，只是：

  1. 启动前新增一次 sortPeriodics()，把两组节点按 execOrder_ 排好序；
  2. 输入/输出两段遍历统一调用同一个 runPeriodicPhase()，但调用位置保持现状：输入段放 switch 外，输出段放 case RUN 内。
// ── 改造后的 RT 周期 ────────────────────────────────────────────
receiveData();
// … reads taskSched, axis-fault 前置检测（原样） …
runPeriodicPhase(factory_.inputPeriodics);        // INPUT：switch 外，所有状态（位置同 L152）
switch (taskScheduling_) {
  case RUN:
    // …命令节点调度（原样 L171-232）…
    runPeriodicPhase(factory_.outputPeriodics);    // OUTPUT：case RUN 内，仅 RUN（位置同 L233）
    break;
  // …其余 case 原样…
}
// …taskSched 回写 + sendData() + 心跳（原样）…

6.3 新增 sortPeriodics()（NodeFactory）

只在 run() 启动前调用一次（RT 线程 rtos_task_create() 之前），热路径零开销；stable_sort 保证 execOrder_ 相等时保持注册顺序。

// NodeFactory.cpp
#include <algorithm>
void NodeFactory::sortPeriodics() {
    const auto byOrder = [](const auto& a, const auto& b) {
        return a->execOrder_ < b->execOrder_;
    };
    std::stable_sort(inputPeriodics.begin(),  inputPeriodics.end(),  byOrder);
    std::stable_sort(outputPeriodics.begin(), outputPeriodics.end(), byOrder);
}
调用时机：sortPeriodics() 必须放在 registered()/modelRegistry_ 注入 之后、rtos_task_create() 之前，位于 NodeManager::run()。它不属于 RT 回调，因此不违反实时约束。

6.4 新增 runPeriodicPhase()（NodeManager 私有辅助）

把 L152-167 与 L233-248 两段复制粘贴循环抽成唯一实现（含"首次 init + 每周期 execute + 失败诊断"）。

// NodeManager.h 私有成员
void runPeriodicPhase(const std::vector<std::shared_ptr<PeriodicNode>>& nodes);

// NodeManager.cpp
void NodeManager::runPeriodicPhase(const std::vector<std::shared_ptr<PeriodicNode>>& nodes) {
    for (auto& node : nodes) {
        if (node->getNodeStatus() == NodeStatus::RTINIT) {
            node->init();
            node->setNodeStatus(NodeStatus::EXECUTING);
        } else if (node->getNodeStatus() == NodeStatus::EXECUTING) {
            node->execute();
        } else {
            ERROR_PRINT("%s 执行失败\n", node->getNodeName().c_str());
        }
    }
}

6.5 组件差异：只有"分层"与"控制位置"

组件改造前改造后执行条件
receiveData / sendDataControllerController（不动）所有状态
输入段inPutNodes 手写循环runPeriodicPhase(inputPeriodics)所有状态（switch 外）
命令段cmdNode_->execute()不变仅 RUN
输出段outPutNodes 手写循环runPeriodicPhase(outputPeriodics)仅 RUN（case RUN 内）

6.6 组内顺序生效示例

execOrder_ 只影响同一相位内部先后，不改变跨相位次序。例如 OUTPUT 相位按 80→90→100 执行：

receiveData
  → INPUT:  DataPub(10)                    // 采集/读反馈
  → 命令段: 速度规划（Ruckig）             // 若 RUN 且有活动命令
  → OUTPUT: ContinuousJog(80) → MujocoIdentPub(90) → PlcLogicNode(100)
  → sendData

6.7 需要同步改动的两处周边

  1. 启动注入（NodeManager.cpp L29-37、L49-56）：把对 inPutNodes/outPutNodes 的 registered() 与 modelRegistry_ 注入，改为遍历 inputPeriodics/outputPeriodics。字段名与类型调整即可，逻辑不变。
  2. 命令准备段（L65-77）：仅涉及 CmdNode，保持不动。
结论：调度器改造 = ① 启动前一次 sortPeriodics() + ② 两段循环抽成 runPeriodicPhase() + ③ 容器指向新字段。RT 回调的调用位置与执行条件逐条保持现状，相位总顺序（输入→命令→输出→sendData）与"输入段全状态、输出段仅 RUN"的不对称语义均不回归。

7. 现有节点归类与推荐顺序

7.1 长期节点迁移表

节点现状目标相位推荐 execOrder_说明
DataPubINPUTINPUT10读数据/采集，最前
ContinuousJogOUTPUTOUTPUT80常驻点动（会规划），输出相位
MujocoIdentPubOUTPUTOUTPUT90可仿真，发布采样
PlcLogicNodeOUTPUTOUTPUT100PLC 逻辑/联锁层，最后

7.2 顺序约定建议

  • INPUT 相位：采集 / 读反馈优先（DataPub）。
  • OUTPUT 相位：运动生成（ContinuousJog，80）→ 数据发布/观测（MujocoIdentPub，90）→ 逻辑/联锁（PLC，100）。
  • 用 10 的倍数留出插入空间；同值稳定靠注册顺序。

7.3 命令节点（保持不动）

Enable / Disable / JogJ / MoveAbs / MoveL / MoveJ / MoveC / MovePath / Movehome / MoveSine / MoveV / MoveExcite / MoveCurve / Reset / Setmode / SetZero … 全部继续用 REGISTERCMD + CmdNode，零改动。

8. 迁移步骤

步骤 1步骤 2步骤 3步骤 4步骤 5步骤 6
  1. 基类改造：在 BaseNodeInterface.h 新增 NodePhase 枚举与 PeriodicNode 类；实现 PeriodicNode::execute()（取 OutputNode::execute/InputNode::execute 的唯一实现）。暂时保留旧类作别名或占位，便于编译期渐进。
  2. 注册机制：在 NodeFactory.h/.cpp 新增 RegisterPeriodic 模板 + REGISTER_PERIODIC 宏；新增 sortPeriodics()，容器类型改为 shared_ptr<PeriodicNode>。旧宏 REGISTERINPUT/OUTPUT 暂时转发到新宏（默认 order=10）。
  3. 子类迁移：DataPub、MujocoIdentPub、PlcLogicNode、ContinuousJog 改继承 PeriodicNode，并把注册宏换成 REGISTER_PERIODIC(…, INPUT/OUTPUT, order)（见 §7.1 表格）。逐个文件改，单一提交可控。
  4. 调度器：NodeManager::run() 启动前调用 factory_.sortPeriodics()（§6.3）；新增 runPeriodicPhase() 统一两段循环（§6.4），改遍历 inputPeriodics/outputPeriodics（§6.5、§6.7）。调用位置与执行条件逐条保留——输入段仍在 switch 外（全状态），输出段仍在 case RUN 内（仅 RUN），见 §6.1。
  5. 清理旧类：确认无引用后删除 InputNode/OutputNode 及重复 execute() 实现，删除 / 收窄旧宏。
  6. 文档与回归：更新本计划书状态、CMakeLists 注释、相关头文件注释；跑现有测试。
兼容策略：步骤 1-4 期间新旧宏可并存（旧宏转发到新宏），实现平滑迁移、随时可回退。第 5 步删除旧类前，务必全局 grep 确认无 InputNode/OutputNode 引用。

9. 风险与验证

风险等级缓解措施
重构改变节点执行顺序 / 相位回归高排序只在启动前一次；STL stable_sort 保证同值保持注册序；对照 §7.1 顺序核对日志顺序。
RT 循环内意外引入分配/排序中sortPeriodics() 只在 run() 启动前调用；RT 回调内保持线性遍历。
静态初始化顺序不确定导致排序结果抖动低稳定靠 execOrder_ 显式值而非注册序；separate 不依赖跨 TU 静态初始化次序（NodeFactory 运行时构建时 drain）。
旧宏兼容层长期残留低迁移完成（步骤 5）后删除旧宏，收敛到单一 REGISTER_PERIODIC。
ContinuousJog 语义归属争议中归入 OUTPUT 相位（execOrder_=80），不改变其行为；如需真正"命令化"可后续单独立项，不在本重构内。

验证清单

  1. 编建通过（含 MatIEC PLC 生成路径，若启用）。
  2. 仿真模式跑通：确认周期顺序仍为 输入→命令→输出→sendData。
  3. 用日志 / 观测确认 DataPub 先于 PlcLogicNode。
  4. 修改某节点 execOrder_ 后确认顺序随之变化（验证排序生效）。
  5. 确认 RT 循环内无分配 / 无异常 / 无阻塞（静态扫描）。

10. 收益与回滚

10.1 收益

  • 消除重复：InputNode/OutputNode 两份相同实现合一，减少 ~50 行重复。
  • 顺序可控：从"链接看缘分"变为"execOrder_ 显式定义"，新增节点可插入任意位置而不影响他人。
  • 语义清晰：两维（触发 / 相位）正交，CODING 时归类不再凭感觉。
  • RT 合规：排序移出热路径，循环内仍是线性遍历，开销零。

10.2 回滚策略

因采用"新旧并存 + 渐进迁移"，任一步骤失败均可通过恢复对应 git 提交回滚。建议每个迁移步骤独立提交，便于二分定位。

10.3 后续可选方向（不在本计划内）

  • 把 ContinuousJog 正式"命令化"（从常驻标志位改为 CmdNode 事件驱动）。
  • 为 PLC 引入"浅入深出"的 pre/post 双相位（并入本 plan 的 Phase 扩展，需额外设计）。
